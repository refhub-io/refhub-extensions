# Contributing to refhub-extensions

This is the process guide for the RefHub browser extension repo.

## Brand, style, and identity

Before changing popup UI, store copy, messages, screenshots, or docs, use `refhub-style-guide/refhub-identity.md` as the brand reference. Preserve the RefHub voice, visual system, dark-first feel, and explicit user-action capture model.

Core rules:

- Prefer concise, practical wording over marketing copy.
- Preserve lowercase, `//` comment-style headings, snake_case labels, and monospace conventions where the repo surface already uses them.
- Keep examples concrete and operational: vaults, papers, tags, relations, PDFs, exports, agents, and API keys.
- Do not introduce a one-off visual, copy, naming, or interaction style for a single feature.

## Existing conventions

Before changing behavior, read `README.md` and nearby files in `src/js/` and `src/styles/`.

Preserve the extension model:

- one shared source tree;
- browser-specific manifests generated by `scripts/build.mjs`;
- `activeTab` plus explicit user action for capture;
- production endpoints locked unless custom URLs are enabled for dev/self-hosted builds;
- RefHub brand voice and visual system from `refhub-style-guide/refhub-identity.md`.

## Scope and branch discipline

Do the work that was asked for. Keep unrelated refactors, permission changes, dependency churn, formatting sweeps, and store-copy edits out of focused PRs unless they are required.

## Pull requests

Never commit directly to `main`.

Use a fresh branch from current `origin/main`:

- `fix/...` for bugs.
- `feature/...` for new capture/save behavior.
- `docs/...` for documentation-only changes.
- `chore/...` for maintenance.

Open a PR for every change.

## Verification

Run:

```sh
npm run build
```

For behavior changes, load the generated extension locally in Chrome/Chromium and Firefox when relevant:

- Chrome/Chromium: load unpacked from `dist/chrome`.
- Firefox: load temporary add-on from `dist/firefox/manifest.json`.

Verify permissions, endpoint config, popup layout, save flow, and post-save routing for the changed surface.

## Changelog and semver

If the repo has a `CHANGELOG.md`, update it in the same PR as the shipped change. If a shipped change needs release notes and no changelog exists yet, create one using Keep a Changelog and Semantic Versioning.

Bump `package.json` for shipped extension behavior changes:

- Patch: fixes and small docs/packaging corrections.
- Minor: new capture behavior, settings, or supported site types.
- Major: breaking storage schema, permission model, endpoint model, or install expectations.

Release tags should use the `vX.Y.Z` form for new releases. The historical `2.0.0` tag predates that convention.

Do not widen browser permissions without explicitly explaining why in the PR.

## Security and credentials

Never commit API keys, bearer tokens, local env files, private user data, or user-specific credentials. Examples must use placeholders only.
